# Question: Step (c) didn't duplicate anything, but Q1 showed the class ETL did.
#           What changed? You didn't touch the dimension INSERT.
#
# Explanation:
# In the class warehouse schema, dim_driver(driver_id) and dim_passenger(passenger_id)
# lacked UNIQUE constraints. Although the SQL query had ON CONFLICT DO NOTHING,
# Postgres without a unique constraint or index target could not detect conflicts
# on the natural keys, so each execution inserted fresh rows with new serial
# primary keys (driver_key, passenger_key).
#
# In warehouse_migration.sql (Part 2), we added explicit UNIQUE constraints:
#   ALTER TABLE dim_driver ADD CONSTRAINT uq_dim_driver_driver_id UNIQUE (driver_id);
#   ALTER TABLE dim_passenger ADD CONSTRAINT uq_dim_passenger_passenger_id UNIQUE (passenger_id);
#
# In etl_pipeline.py, load_dim() executes:
#   INSERT INTO dim_driver (...) VALUES (...) ON CONFLICT (driver_id) DO NOTHING;
# Because driver_id and passenger_id now have UNIQUE constraints, Postgres can
# detect existing keys during conflict arbitration and skip insertion.
# On the fact table, fact_trips has UNIQUE (source_trip_id) and uses
# ON CONFLICT (source_trip_id) DO UPDATE, performing an idempotent upsert rather
# than appending duplicates.
# ==============================================================================
